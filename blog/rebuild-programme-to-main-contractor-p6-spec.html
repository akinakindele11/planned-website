How to Rebuild a Construction Programme to Your Main Contractor's Primavera P6 Specification

Published September 2026 6 min read Programme Compliance

You built the programme in MS Project, the job is moving, and then the main contractor tells you it has to be in Primavera P6, to their specification, with weekly updates. This is common on NEC and large infrastructure jobs, and a straight export will not pass. Here is what the client is actually asking for and how to get your programme accepted.

Why the Main Contractor Wants P6

On most public and large private programmes the client runs Primavera P6 and needs every contractor's schedule in the same tool, so it can be integrated, progressed and audited in one place. On NEC contracts the accepted programme is a contractual document, so the client cares that the logic is sound and defensible, not just that a Gantt chart exists. P6 is where they can check that.

What "To Our P6 Spec" Usually Means

A client P6 specification is a real document, and it is specific. A typical one requires:

  • Primavera P6, a stated version or later, with the native files delivered: .xer, and often .xml and .plf, plus a PDF and a written narrative.
  • Set project settings: physical percent complete, fixed duration and units, retained logic, and the critical path defined as the longest path and shown in red.
  • The client's own activity coding structure, applied across every activity and not changed for the life of the job.
  • Activity rules: unique activity IDs that never change, finish to start logic, short durations, minimal leads and lags, no start to finish links, no open ends, and no constraints.
  • A weighting system, man hours and resources, so progress can be measured properly.
  • S curves and resource histograms.
  • A submission cadence, commonly a weekly update by a set time each Monday and a monthly update, each as a native file and PDF.

If you have not seen the specification yet, ask for it. It is usually an appendix to the technical documents, and it is what your programme will be judged against.

Where Converted Programmes Usually Fail

Most rejected programmes fail for the same reasons:

  • The programme was exported from MS Project rather than rebuilt, so it carries constraints, open ends and broken logic that the specification forbids.
  • Testing and commissioning and handover are left as outline only, with no real durations or logic, so there is no true completion date.
  • Finishes are sequenced too early, which the client will not accept because it risks damage and rework late in the job.
  • The interfaces with the client's other trades are not modelled, so there are no access windows for them.
  • Review periods, activity durations or the critical path do not match what the contract and the specification require.

How to Get It Accepted

  • Rebuild it in P6, do not export it. Build the logic to comply with the specification from the start.
  • Build the missing phases properly, especially testing and commissioning and handover, so the programme has a real end date.
  • Model the interfaces and access windows for the other trades, and sequence the finishes with an end of job revisit for final paint, floors and ceilings.
  • Apply the client's activity codes and the required settings, and produce the critical path, S curves and histograms.
  • Then run the weekly and monthly updates to the specification, so the programme stays accepted, not just accepted once.

Expect a comment cycle. The client will usually mark up the first submission and hold a programme workshop to agree access dates with the other trades. Getting the baseline accepted quickly matters, because until it is, you are running the job without an agreed programme to measure delay or an extension of time against.
